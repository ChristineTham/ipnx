## documented build steps

`.catalog.c` is a **5620/jerq (WE32100) terminal program**, not a VAX program, and
nothing in this chunk builds it:

- `.catalog.c:2-3` — `#include <jerq.h>`, `#include <font.h>`: the jerq include set
  (`/usr/jerq/include`, which docs/v10-dist.md settles from jerq's own sources).
- It calls only the jerq runtime — `alloc`, `balloc`, `bitblt`, `rectf`, `segment`,
  `string`, `request(KBD|MOUSE)`, `wait(KBD|MOUSE|RCV)`, `own()`, `rcvchar()`,
  `kbdchar()`, `cursinhibit()`/`cursallow()`, `Drect`, `display`, `defont` — so it
  is compiled by the jerq cross-toolchain and downloaded as a `.m`, never linked by
  `/bin/ld`.
- **There is no makefile/mkfile in face48.** The only build product is the committed
  `.catalog.m` beside it (12138 bytes, `file` says `data`, mtime Jul 3 1984), which
  is not in this chunk's list.

`.catalog.c:69-73` fixes the wire format the catalog consumes, and it is **not** the
format of the files in this chunk:

```
   for(i=0; i<48; i++){
     for(j=0; j<48/8; j++)
	bp[i*48/8+j]=getc();
     bp+=2;	/* MAC-32 to the rescue */
   }
```

48 rows x 6 bytes of **raw binary** preceded by a NUL-terminated name
(`.catalog.c:67-68`), with `bp+=2` padding each scanline to 64 bits for the WE32100.
The files in this chunk are ASCII hex. So `.catalog.c` is the *receiver* on the
terminal end; something on the VAX side reads these files and pushes binary down the
wire. Nothing in this chunk is that something.

`.catalog.c:137,152` — `int ArgCount;` is declared and tested
(`... && (ArgCount>2)`) but **never assigned**, so the "wait for a keystroke between
pages" branch is dead. A paging bug, not an install matter.

## contradictions and traps

1. **face48 has no `CATALOG` wrapper, while all three sibling icon directories do.**
   `git ls-files` shows `v10/usr/jerq/icon/16x16/CATALOG`, `.../texture/CATALOG` and
   `.../large/CATALOG`, each exactly one line — `jx CATALOG.m $*`. face48 has only
   `.catalog.c` and `.catalog.m` (dot-prefixed, lowercase) and **no wrapper at all**,
   so the documented invocation `CATALOG *` does not exist here; it must be run as
   `jx .catalog.m *`. Verified by `git ls-files`, not `ls`.

2. **`v10/usr/jerq/icon/README` never mentions face48, and its stated search path
   omits it — but `icon.c` includes it.** README:13-16 says the editor "automatically
   searches the current directory, and then `"/usr/jerq/icon/16x16"`,
   `"/usr/jerq/icon/texture"` and `"/usr/jerq/icon/large"` in turn" — three
   directories. `v10/usr/jerq/src/icon.c:1028-1034` has **four**, face48 last. The
   README is stale relative to the source; believe `icon.c`.

3. **README's A..Z rule makes three files in this chunk undrawable.**
   `v10/usr/jerq/icon/README:36-38`: `Note: the CATALOG programs assume that the icon
   names start with a character different from 'A'..'Z'. No attempts are made to draw
   icons starting with 'A'..'Z'.` This chunk has `ACSnet`, `FURUTA` and
   `MAILER-DAEMON`. `.catalog.c` itself contains no such filter, and face48 has no
   wrapper script to hold one (trap 1), so for face48 the filter exists nowhere —
   the note describes the sibling `CATALOG` scripts.

4. **`faceS` is a genuinely ZERO-BYTE tracked file.** `git ls-files -s` gives blob
   `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391`, the empty blob — so it is empty in the
   repository, not a local truncation. Spelling verified as capital `S` via
   `git ls-files`. `.catalog.c`'s `OpLoad()` would block in `getc()` forever on it,
   and the A..Z note does not exclude it because its *first* character is lowercase.

5. **`ivette` is truncated mid-file.** 764 bytes, 31 lines; the last line is
   `0x007d, 0x8081` — two words, no third, no newline. A 48x48 face needs 48 rows of
   three words; this has 30 complete rows plus a fragment.

6. **`v10/usr/630/icons/face48/` is a partially byte-identical duplicate tree with
   different names, and it is the one with a packaging rule.** It holds 34 tracked
   files (32 icons + `ICON.LST` + `SOURCE`) against our 862, and
   `v10/usr/630/makefile:369` cpios it to `$(TAPEROOT)/icons/face48` from its
   `SOURCE` manifest. Measured with `cmp`:
   - **15 of the 17 shared names are byte-identical** to ours: `adm ap bart bbc bgs
     bin bwk chaos cow daemon davef dectalk dmr jdj jerq`.
   - `630/icons/face48/acsnet` is **byte-identical to our `ACSnet`**, and
     `630/icons/face48/mailerdaemon` is **byte-identical to our `MAILER-DAEMON`** —
     the 630 tree carries the same two images under lowercase, hyphen-free names.
     Independent corroboration that the uppercase spellings in this chunk were a
     known problem (trap 3).
   - `dan` and `ecc` are **different images under the same name** (1056 vs 1152
     bytes, and still different after stripping whitespace). Which copy installs
     changes what the user sees.
   The `SOURCE` manifest is **not** stale — all 34 names it lists exist, and
   `ICON.LST` lists the same set minus `ICON.LST` and `SOURCE` themselves.

7. **`court` and `court.old` are byte-identical but separate inodes.**
   md5 `574375c5c803d665097783caa15081a6` for both; inodes 166824023 and 166824025,
   1152 bytes each. A real duplicate file, not a hard link. (`court.new`, inode
   166824024, is a genuinely different image.)

8. **Two files in this chunk are one inode with a file in a later chunk.**
   `stat` link count 2 on both:
   - `face48/ches` and `face48/njit_bc` are inode 166824001 (`njit_bc` is in
     chunk 018)
   - `face48/gale` and `face48/wag` are inode 166824141 (`wag` is in chunk 017)
   Any install that copies file-by-file silently doubles the storage and breaks the
   identity; `v10tapes/HARDLINKS` is where the tape's own record of this lives.

9. **`japan` is `bwk` with a new bottom half.** Its first 15 rows are byte-identical
   to `bwk`'s first 15 (verified by `diff` on `head -15`); the remaining 33 rows
   differ. Not a build fact, but it means `bwk` and `japan` are not independent
   artefacts.

10. **`indy` is not 48x48.** 1776 bytes: 48 rows of three **32-bit** words
    (`0x00000000, 0x0001ffff, 0xffa00000,`) = 96 bits per row, i.e. a 96x48 bitmap in
    a directory named face48, read by a program that hardcodes `#define ICONSIZE 48`
    and `48/8` bytes per row (`.catalog.c:9,70-71`).

11. **Two incompatible textual formats coexist**, so any parser must accept both:
    word separator is `", "` in some files and `","` in others, and hex digits are
    uppercase in some (`0x0FF8`) and lowercase in others (`0x0ff8`). The two spellings
    are exactly the 1152-byte and 1056-byte size classes.

12. **`/usr/blit/bin/face` is a different `face48` entirely** — `:6` is
    `jx /usr/blit/mbin/face48.m $*`, a downloadable program named `face48.m` under

    them.

13. **`v10/usr/src/build/ipnx.tar` contains face48 paths** — a committed tar in the
    build directory that already holds copies of these files. A committed build
    product beside the build system that would produce it.

14. **The man page and the C code name the same directory through different roots.**
    `cmd/face/file.c:38` says `/usr/jerq/icon/face48`; `man9/faced.9:139,159` says
    `/n/kwee/usr/jerq/icon/face48`. `faced.9` is describing the face *server*, which
    reaches every machine's copy through the `/n/<machine>` name space, so the two are
    consistent only if the machine is `kwee`. Nothing in the tree makes `/n/kwee` an
    install target; the destination to build to is the `/usr/...` one.
    `v10/usr/man/adm/man9/faced.9` is a second copy of the same page carrying the
    same two lines.

15. **No case collision among the 862 direct children** — checked with `git ls-files`
    (APFS `ls` cannot be trusted here), and no `u_`-prefixed twin exists anywhere in
    face48. The names `andrew`, `bart`, `jhc`, `pat`, `pg`, `rob` each appear twice
    under face48, but always in *different* directories — `old/andrew`, `old/pg`,
    `old/rob`, `mohawk/bart`, `safe/bart`, `safe/jhc`, `safe/pat` — so no renaming
    rule applies. The top-level `andrew` and `bart` in this chunk are distinct files
    from those.

## files with no build contribution

**356 of 357.** Every face-bitmap data file carries no build step, no flag, no
ordering constraint and no destination: each is 48 lines of three comma-separated hex
words, one 48x48 monochrome portrait per login name, host, or joke — the content side
of V10's "faces" mail feature. Their exceptions are anomalies of *content*, not of
build: `faceS` (empty), `ivette` (truncated), `indy` (96x48), `court`/`court.old`
(identical), `ches`/`gale` (hard-linked out of the chunk).

`blank.face` carries no build rule either, but is the one data file **named by
absolute path** in code outside the chunk (`jerq/src/face/face.c:13`), so an install
that drops it breaks the face viewer's fallback.

`.catalog.c` is the only file in the chunk with build meaning, and what it documents
is a jerq-toolchain compile that nothing here invokes.

### how "no hidden prose" was verified

Every one of the 356 data files was read in full via `cat`, and separately every byte
of all 356 was passed through `tr -d '0-9a-fA-FxX, \t\n'`: the residue is **zero
bytes in every file**. There is no comment, no name, no path and no prose hidden in
any of them.
