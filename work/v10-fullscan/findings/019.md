## documented build steps

- **`jx` is the tool beyond cc/as/ld here.** Every launcher in the icon tree is `jx <name>.m`;
  `.m` is the 5620/jerq downloadable image. `jx` itself is committed only as
  `v10/usr/630/bin/jx` and `v10/usr/blit/bin/jx`; its source is `v10/usr/jerq/src/jx/jx.c`.
  There is **no** `/usr/jerq/bin/jx`, which is where `demo:1`'s PATH expects it.
- **`32ld` is the stand-alone downloader** — `v10/usr/jerq/demo/stand-alone/demo:8` is `32ld $1`.
  Source `v10/usr/jerq/src/32ld/32ld.c`; man pages `v10/usr/man/man9/32ld.9`.
- **`mstrip` strips 5620 images** — `swar/makefile:8`. Committed only under blit
  (`v10/usr/blit/bin/mstrip`, source `v10/usr/blit/m/src/mstrip.c`); nothing named `mstrip`
  exists under `v10/usr/jerq/`.
- **swar's makefile targets** are `swar` (default), `install`, `clean`.
  `makefile:1` `CC=3cc`; `:2` `CFLAGS=`; `:4` `${CC} $(CFLAGS) swar.o -o swar`;
  `:9-10` `clean:` / `rm -f *.o m.out core swar` — `m.out` is the 5620 compiler's default output
  name (the local analogue of `a.out`), so the toolchain writes `m.out` unless given `-o`.
- **swar's real build inputs are the `.icon` files, and the makefile says so.**
  `makefile:5` `swar.o: player0.icon player1.icon accel.h missile.icon deathstar.icon boom.icon`.
  `swar.c:21-40` and `:62-66` `#include` each of them as bare initialiser bodies inside
  `short xxbits[]={ … };` and `struct dv dv[NORIENTATION]={ … };`, so they are compile-time
  inputs, not runtime data — the only files in this chunk that are.
- **The pixel dimensions of swar's icons live only in `swar.c`, not in the data files** —
  the "table in another program" authority for this directory:
  `swar.c:24` `Bitmap stardwg={(Word *)starbits, 1, 0, 0, 16, 16};`
  `swar.c:28` `Bitmap p0dwg={(Word *)p0bits, 2, 0, 0, 44, 44};`
  `swar.c:32` `Bitmap p1dwg={(Word *)p1bits, 2, 0, 0, 44, 44};`
  `swar.c:36` `Bitmap misdwg={(Word *)misbits, 1, 0, 0, 32, 32};`
  `swar.c:40` `Bitmap boomdwg={(Word *)boombits, 2, 0, 0, 64, 64};`
  and `swar.c:281` `register dx=dwg%4*o->diameter, dy=dwg/4*o->diameter;` makes each a **4x4
  sprite sheet** of `diameter`-sized cells.
- **Four incompatible icon-file formats, all in this chunk.** Measured, every file:
  1. `16x16/` and `texture/` — a named C-style initialiser: `Texture <name> = {` (or without the
     `=`), then exactly **sixteen 16-bit** `0x` values, then `};`. All 211 + 70 files have
     exactly one `{` and exactly sixteen `0x` values. **No wrong-dimension file.**
  2. `large/` — bare `0xXXXX,` rows, **no braces and no name**; value count per line varies
     1..4 and line count 4..50, so dimensions come from the file's own shape. Measured `0x`
     counts: 200 (x6), 144 (x3), 96 (x3), 140, 126, 111, 102, 100, 80, 78, 64 (x2), 56, 52, 50,
     48, 41 (x2), 38 (x9), 32, 14, 12.
  3. `48x48x2/` — bare **32-bit** `0x00000000,` rows: all 141 files are exactly 48 lines x 3
     values x 32 bits = 96 bits per row = **48 px at 2 bits/pixel**, 1776 bytes each.
  4. `face48/{mohawk,old,safe}/` — the same bare layout but **16-bit** words: 48 lines x 3 x 16
     bits = **48 px at 1 bit/pixel**.
  5. `sapengo/icons/` — bare `0xXXXX,` rows, tab-indented, no braces, no name; 47 files are
     32 lines x 2 values (32x32) and 6 (`0diamond blank block egg fblock null`) are 8 lines x
     8 values.
- `large/CATALOG.c` is the only reader here that accepts two formats and it labels one:
  `:73` `/* old format */` — a file whose first hex digit is *not* followed by `x`, read as raw
  nibbles, one row per line. The `0x`-prefixed branch (`:89-108`) is the other.
- `texture/CATALOG.c:49` `b = balloc(Rect(0,0,48,48));` implements README:31's "48x48 areas";
  `16x16/CATALOG.c:86` `b = balloc(Rect(0,0,16,16));` and `:122-126` the 32-px grid pitch.

## contradictions and traps

1. **`v10/usr/jerq/icon/texture/INSPECT.m` is tracked in git but MISSING from the working tree.**
   `git status --porcelain` reports ` D v10/usr/jerq/icon/texture/INSPECT.m`; the 12012-byte blob
   `09f45b9f4f7288a81ef5b32d19e26e239e522dc5` is in the index and
   `v10superset/jerq/icon/texture/INSPECT.m` is intact on disk (12012 B, Apr 20 1983). So
   `INSPECT`'s only line — `jx /usr/jerq/icon/texture/INSPECT.m` — names a file `v10/` does not
   currently have, while all three sibling `CATALOG.m` files are present.
2. **`v10/usr/jerq/bin/` is EMPTY in this distribution.** `git ls-files 'v10/usr/jerq/bin/*'`
   returns 0 paths. README:13 names `/usr/jerq/bin/icon` as the icon editor — the program whose
   documented search path (README:14-16) is the entire reason the three icon directories exist —
   and **no such program exists anywhere in the tree** (nothing under `v10/usr/jerq/src/` builds
   an `icon`). `demo:1` also puts `/usr/jerq/bin` on PATH for `32ld`/`jx`, neither of which is
   there. The built jerq host tools live under `v10/usr/blit/bin/` and `v10/usr/630/bin/`.
   So the packaging rule for the only consumer of this chunk's 320 icons cannot be satisfied
   from this tree.
3. **`swar.c`'s own build line contradicts its makefile.** `swar.c:1` is
   `/*% mcc -g % -o swar` — the jerq `%`-comment convention giving the compile command — naming
   **`mcc`**; `makefile:1` is `CC=3cc`. `swar.c:326` `/*mcc bug */` corroborates `mcc` as the
   compiler actually used. `mcc` is committed only as `v10/usr/blit/bin/mcc` (source
   `v10/usr/blit/m/src/mcc.c`); `3cc`'s source is `v10/usr/jerq/sgs/3cc.c`. Two different
   compilers for one file, from two different trees, and the makefile is the newer of the two
   statements only by convention — nothing here settles it.
4. **swar installs into a directory that holds only its launcher.**
   `git ls-files 'v10/usr/jerq/demo/mux/*'` returns exactly one path,
   `v10/usr/jerq/demo/mux/demo`. `makefile:7` copies `swar` there, and that launcher has a
   dedicated case for it — `swar)	echo "type 'Q' to exit"` / `sleep 2` / `32ld $1` — so the
   launcher expects a `/usr/jerq/demo/mux/swar` the tree does not ship. The install *name*
   matches; only the artefact is absent.
5. **`stand-alone/demo` lists an empty directory, and filters out the only names it could
   print.** `git ls-files 'v10/usr/jerq/demo/stand-alone/*'` returns exactly one path — `demo`
   itself. Its menu command (`demo:6`) is
   `ls /usr/jerq/demo/stand-alone | egrep -v "demo|jciferr" | pr -t -6 -l1`, so `demo` with no
   argument prints `Available demos are:` and then nothing. `jciferr`, the name the egrep goes
   out of its way to exclude, is not in the tree either. Meanwhile
   `v10/usr/jerq/demo/` holds ~40 stand-alone-looking sources (`bounce.c`, `mazewar.c`,
   `pacman`, `pengo`, …) one level up — the sources are there, the populated install directory
   this launcher reads is not.
6. **The three `CATALOG` scripts are byte-identical but are three separate files, not one
   inode.** `git ls-files -s` gives all three blob
   `14061a2c6547bac3fe7dcafb07bb29e1a0f34ae5`; `ls -i` gives 166823536 / 166824769 / 166824811.
   A file-by-file install is correct; a dedup-by-hash or hardlink-by-content install would
   collapse them and **break two of the three directories**, because the script is
   **cwd-relative** (`jx CATALOG.m $*`) and each directory has its own *different* `CATALOG.m`:
   blobs `272c8ab9` (16x16, 10111 B), `dadcc3c3` (large, 10757 B), `826f6e67` (texture, 8629 B).
7. **`INSPECT` is absolute where `CATALOG` is relative — but README's cd instruction is still
   load-bearing, for a different reason than it gives.** README:19 says
   `type "INSPECT" in the "texture" directory`. INSPECT's `.m` path is absolute so the launcher
   runs from anywhere; but `INSPECT.c:79` `OpLoad(tex,FNAME)` opens the texture *name the user
   types* with no directory prefix, so cwd still has to be `texture/`. The README is right about
   the requirement and wrong about which line creates it.
8. **`48x48x2/` cannot be read by any reader in this chunk.** Its words are 32-bit
   (`0x00000000`) and every `scanhex` here consumes exactly four nibbles then resynchronises on
   the next `'0'` byte — `16x16/CATALOG.c:53-58`, `texture/CATALOG.c:17-22`, `INSPECT.c:55-57`,
   all `while((ch=getc(fp)) != '0'); getc(fp); /* 'x' */` followed by four `hex(getc(fp))`. In
   `0x00000000` the resync character is the very next byte, so the parse desynchronises
   immediately. `large/CATALOG.c`'s `0x` branch (`:92-107`) makes the same four-nibble
   assumption. So `48x48x2` belongs to a **different program** — the `face`/`vismon` family
   (cf. `v10/usr/src/cmd/face/file.c`, the authority cited for `face48` elsewhere in this pass)
   — despite living under `/usr/jerq/icon`. README lists only three directories (`16x16`,
   `large`, `texture`) and names neither `48x48x2` nor `face48`; the icon editor's documented
   search path deliberately excludes both.
9. **`16x16/CATALOG.c` and `texture/CATALOG.c` silently render a blank icon for any file with no
   `{`.** `16x16/CATALOG.c:72` and `texture/CATALOG.c:36` are both
   `if (ch==EOF) for (i=0; i<16; i++) tex->bits[i] = 0;`. Every `large/`, `48x48x2/`, `face48/`
   and `sapengo/` file lacks a `{`, so pointing either CATALOG at one produces an empty square
   and no error. Worse: **that is byte-for-byte the same result as the legitimate texture
   `white`**, whose sixteen values are all `0x0000` — so a failed load is indistinguishable from
   a successful one.
10. **`INSPECT.c` drops that guard and hangs instead.** `INSPECT.c:69-70` is
    `while ((ch!='{')&&(ch!=EOF)) ch=getc(fp);` followed *directly* by
    `for (i=0; i<16; i++) {tex->bits[i] = scanhex(fp); getc(fp);}` — the `ch==EOF` branch that
    `CATALOG.c:36` has is gone. `scanhex`'s `while((ch=getc(fp)) != '0');` never terminates at
    EOF (`getc` returns −1 forever). Naming a non-`{` file at INSPECT's `Texture:` prompt is an
    infinite loop, and every `large/`, `48x48x2/`, `face48/` and `sapengo/` file qualifies.
11. **`texture/CATALOG.c` and `INSPECT.c` accept only UPPERCASE hex.** `texture/CATALOG.c:6-10`
    and `INSPECT.c:45-49` are both
    `if ((ch>='0') && (ch<='9')) return(ch-'0'); return(10+ch-'A');` — no lowercase branch and
    no bounds check — where `16x16/CATALOG.c:40-46` handles `A`–`F` *and* `a`–`f`. Verified: **no
    `texture/` icon uses lowercase hex**, so library and reader agree today; but the icon
    editor's documented search path (README:14-16) reaches `texture/` from cwd, and **102 of the
    211 `16x16/` icons are lowercase**, so any of those saved into `texture/` renders wrong with
    no error.
12. **All three CATALOG programs skip any icon whose name starts `A`–`Z`, and real icons are
    caught by it.** `16x16/CATALOG.c:117`, `large/CATALOG.c:137` and `texture/CATALOG.c:57` are
    each `if ((Name[0]>='A') && (Name[0]<='Z')) return(0);`, and README:36-38 states the rule
    (`the CATALOG programs assume that the icon names start with a character different from
    'A'..'Z'. No attempts are made to draw icons starting with 'A'..'Z'.`). The rule exists to
    skip `CATALOG`/`CATALOG.c`/`INSPECT` themselves, but it also makes
    **`16x16/ATTinvlogo`, `16x16/ATTlogo` and `large/ATT` permanently unviewable** by the shipped
    browser — and `ATTinvlogo` is the one file in the tree that names its own install path.
13. **`v10/usr/jerq/icon/foo` is a stale `/n/…` dump manifest, not a manifest of this tree, and
    nothing reads it.** 93 lines of
    `/n/kwee/usr/jerq/icon/48x48x2/<name>//<date> v/v<volume>/<block>` (a `v`-tape volume/block
    listing). Against the 141 icons actually in `48x48x2/`: **8 names in `foo` are absent from
    the tree** — `caryl chris dbm gre koala lalita llc natalie` — and **58 tree icons are absent
    from `foo`** — `adb ak1 anand andys bev car chip cjc court.old crs ddl dhn diana dji
    dluginbu don esther faber frodo gtv isabelle jbl jchin jhs jhv jrr kee kestrel lepac.old
    lil.old mark marko mary mct mia mischu mjp moe neera.old oreo1 pal papa paul pmu pommy
    purush rjh romano rr saad sean.old seanq sharon sjones stan terry timmins zeydy`. `rob` and
    `sally` each appear twice with different dates (`:73`/`:92`, `:75`/`:93`). `/n/kwee/...` is
    a network-namespace path, so treating any line of it as an install target would create a
    directory named `n`.
14. **`face48/` is a second, incompatible face library beside `48x48x2/`, with overlapping
    names.** `face48` files are 48 lines x 3 x **16-bit** words (48x48x1); `48x48x2` files are
    48 lines x 3 x **32-bit** words (48x48x2). `bart pg rob andrew jhc pat` exist in both and
    every pair differs (`cmp`), as do the byte counts (1056/1152 vs 1776). A packaging rule that
    treats `/usr/jerq/icon/*` uniformly will mix two pixel depths.
15. **`face48/safe/` is a *censored* copy, not a backup — and for `bart` the censored one is
    what is live.** `cmp` is silent for `face48/safe/bart` vs the top-level `face48/bart` (both
    1056 B, blob `7fa6d980`), while `face48/mohawk/bart` differs. Reading the data settles which
    is which: `safe/bart` rows 8-16 are solid fill (`0x03FF,0xFFFF,0xFFA0` …) where
    `mohawk/bart` has facial detail in the same rows (`0x03FF,0x0101,0xFFA0`,
    `0x03FC,0x2520,0x3FE0`, …). So `safe/` holds blanked-interior silhouettes and the live face
    is the blanked one. `old/andrew`, `old/rob` and `safe/jhc` differ from their live namesakes
    in *length* (1056 vs 1152), so those three are not simple reverts. Blob hashes of the seven:
    `0aba6fea` old/pg, `56065691` mohawk/bart, `599c0b4a` old/andrew, `7fa6d980` safe/bart,
    `addb3334` old/rob, `e2803383` safe/pat, `e9aaa155` safe/jhc — all distinct.
16. **Committed build products sit beside their sources throughout this tree.**
    `v10/usr/jerq/icon/16x16/CATALOG.m`, `large/CATALOG.m`, `texture/CATALOG.m` (and the missing
    `texture/INSPECT.m`) are 5620 binaries checked in next to `CATALOG.c`/`INSPECT.c`. **V8's
    copy of the same tree has no `.m` files at all** — `git ls-files 'v8/jerq/icon/texture/*'`
    returns only `CATALOG`, `CATALOG.c`, `INSPECT`, `INSPECT.c` — so the `.m` images are a
    V10-tape addition, and a build that regenerates them will overwrite committed artefacts.
17. **`large/CATALOG.c:127` hardcodes a 200x200 scratch bitmap and clips silently.**
    `b = balloc(Rect(0,0,200,200));`, and `putnibble` guards every plot with
    `if (ptinrect(p,clipr)) point(b,p,F_OR);` — no message. The widest `large/` icons carry 200
    `0x` values; nothing in the directory exceeds the limit today, but the reader will crop
    rather than complain.
18. **`INSPECT.c` off-by-one.** `:7` `char FNAME[50];` against `:28` `if (s-t<50)` and `:19`
    `*s = '\0'` — a 50-character name writes its terminator at `FNAME[50]`, one past the array.
19. **`texture/tweed+plus4:4` and `texture/tweeddish` have IDENTICAL pixel data but different
    headers**, so `cmp` says they differ and only a header-stripped hash finds it. Header lines
    are `Texture tweed+cross4:4 = {` and `Texture tweeddish = {` — the *first* also disagrees
    with its own filename. This is the only such pair in the chunk (checked across `16x16/` and
    `texture/` with a header-stripped, case-folded, whitespace-stripped hash).
20. **`48x48x2/court` and `48x48x2/court.old` are byte-identical** (same git blob) — the `.old`
    backup preserves nothing. The other three `.old` pairs (`lepac`, `lil`, `neera`, `sean`) all
    differ, so a "drop the `.old` files" rule is right for `court` and destructive for the rest.
21. **`texture/diagweave` and `texture/weave` declare the SAME name and hold DIFFERENT data.**
    Both headers are `Texture texture/weave = {`; the value blocks differ
    (`0x2626,0x1919,…` vs `0xBFBF,0xA0A0,…`). Anything that installs by declared name rather
    than filename loses one of them.
22. **`16x16/hand` and `16x16/hand-smalltalk` declare the same name `hand`** with different
    data (`0x3F00,0x40FF,0x8C81,…` vs `0x1F00,0x20FE,0x4EC2,…`). Same failure mode.
23. **Two distinct icon-header generations, perfectly correlated with hex case.** Of the 211
    `16x16` icons, **109 use `Texture <name> = {` and all 109 are uppercase-hex; 102 use
    `Texture <name> {` (no `=`) and all 102 are lowercase-hex** — a clean 109/102 split with no
    crossover. The no-`=` form also always has a blank line before `};`. All four readers in
    this chunk skip to `{` and so are indifferent, but the split says two different editors (or
    editor versions) wrote this library, and only the `=` form even resembles C.
24. **The C-looking form is mostly not compilable C.** `Texture <name> = {…};` is a valid
    declaration only if `<name>` is an identifier, and most are not: 28 of the 109 are
    filesystem paths (`/usr/luca/...`, `../16x16/...`), and others carry `-` or `.`
    (`pacghost-d`, `rotminus.icon`, `help.icon`, `blit.icon`, `shearx.icon`, …). The 102 no-`=`
    files are never valid C, and **21 of them have declared names containing spaces, commas,
    parentheses or a trailing colon** — `Texture Fat double headed cursor {`,
    `Texture Charselect, Move mode {`, `Texture Para select cursor, Move mode (English) {`,
    `Texture awCellOff: {`, `Texture Window move cursor {`, and 16 more. Anything that tries to
    `#include` this library as C, or to parse the second token as a name, breaks on them.
25. **Damaged declared names — a capital letter is eaten in a specific family.** `arrow-b` reads
    `Texture awUp rrow {` (the `A` of "awUpArrow" became a space); `drawdoublearr` reads
    `Texture awDbl rrow {`; and `drawbox`/`drawboxthumb`/`drawhalfbox`/`drawsplitbox` read
    `awox` / `awoxThumb:` / `awHalfox` / `awSplitox` — the `B` of "Box" is simply gone.
    `drawcaret` reads `awigCaret`. Sibling names in the same family survive intact (`awTopLeft`,
    `awLeft`, `awCenter:`, `awIdle`, `awThumb:`, `awScroll`, `awCellOn:`), so this is corruption,
    not a naming style. Nothing in this chunk reads the name, but the icon editor writes it back.
26. **109 of 211 `16x16` icons declare a name that is not their filename** (measured). Beyond
    the paths already listed, the outright renames include `george`→`washington`,
    `ATTlogo`→`globe`, `aim-n`→`nsquare`, `aim-p`→`psquare`, `arrow-b-fat`→`awLeft`,
    `arrow-b-turn`→`rotminus.icon`, `arrow-b-wrap`→`reflx.icon`, `arrow-turn`→`arrow-acw`,
    `arrow-wrap`→`arrow-hloop`, `bitblt`→`blit.icon`, `bunny`→`bunny2`, `bunnyface`→`bunny1`,
    `copier`→`copy.icon`, `corner`→`awTopLeft`, `crosshairs`→`crossHairsCircle`,
    `glasses`→`read.icon`, `grab-closed`→`grabc`, `guillotine`→`ghigl`, `impossifork`→`escher`,
    `magnify`→`bigtwo`, `mcsquare`→`einstein`, `oldcar`→`memorial1`, `racecar`→`memorial2`,
    `pen`→`revpen`, `shear`→`shearx.icon`, `startrek`→`trek`, `target3`→`ngtarget`,
    `trashcan`→`erase.icon`, `virus`→`sunspot`, `window-del`→`delete`. In `texture/`:
    `diag3:1`→`structrule`, `grey`→`structdummy`, `tweed`→`structchar` (a group named for
    another application entirely), `fence1/2/3`→`fense1/2/3` (misspelt), `stars1`→`stars2`,
    `tweed+cross`→`nazi`, `bighex`→`texture/bighexagon`, `hex`→`texture/hexagon`.
    **The filename is the only reliable install name.**
27. **Deliberately degenerate data files, easy to mistake for corruption.**
    `texture/white` is sixteen `0x0000` values (blank); `texture/black` is sixteen `0xFFFF`;
    `texture/freckles` is `0x8000` and fifteen `0x0000` (one pixel);
    `sapengo/icons/null` is 64 `0x0000`; `sapengo/icons/blank` is 64 `0xFFFF`. All are intended.
    None is a zero-byte file, and none is the empty git blob (checked: no path in the chunk
    hashes to `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391`).
28. **`swar/missile.icon` is one scan line SHORT of the dimensions `swar.c` declares for it.**
    The file is 31 lines x 2 values = **62 shorts** (465 bytes = 31 x 15). `swar.c:36`
    `Bitmap misdwg={(Word *)misbits, 1, 0, 0, 32, 32};` declares 32 rows x 1 Word (32 bits) =
    32 Words = **64 shorts**. Every other swar icon matches exactly — `deathstar.icon` 16 lines
    x 2 = 32 shorts vs 16 rows x 1 Word = 32; `player0.icon`/`player1.icon` 44 x 4 = 176 vs
    44 x 2 Words = 176; `boom.icon` 64 x 4 = 256 vs 64 x 2 Words = 256. So `misbits[]` is
    declared by its initialiser as 62 elements while `misdwg` describes 64, and `bitblt` on the
    bottom-right 8x8 cell of the 4x4 sprite grid reads two shorts past the array. A build that
    "fixes" the file by padding changes the shipped artefact; a build that trusts `test -s`
    sees nothing wrong.
29. **Trailing whitespace on data lines in 247 of the 540 files** (measured), including
    `sapengo/icons/0diamond` and `sapengo/icons/block` (four spaces after a comma on six of
    eight lines) and every one of the 102 no-`=` `16x16` icons. Harmless to these readers, but
    it defeats naive `diff`/hash comparison against a regenerated file and it is why
    `0diamond` (480 → 520 B) and `block` are larger than their siblings with identical shape.
30. **The `.old`/`safe`/`mohawk`/`old` subdirectory scheme is invisible to the readers.** No
    reader in this chunk descends into a subdirectory; the editor's documented search path
    (README:14-16) names three flat directories. So `face48/{mohawk,old,safe}/` are pure
    archive, reachable only by an explicit cwd + relative name.
