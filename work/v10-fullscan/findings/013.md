## documented build steps

**`CC/` (cfront 2.x C++ headers)**

- `CC/generic.h:4-18` gates token pasting on `BSD`: `#ifdef BSD` gives backslash-newline
  concatenation, `#else` gives `#define name2(a,b)	a/**/b`. Every `Block`/`Map`/`list`/`vector`
  header in both C++ trees pastes through `name2`/`name3`/`name4`, so the whole generic-container
  set is built one way or the other by that one `-DBSD`. On V10's cpp the `/**/` form is the
  working branch.
- Declare/implement pairs, at header scope, that each need exactly one matching `…implement` in
  exactly one translation unit of libC: `CC/Bits.h:11` `Blockdeclare(Bits_chunk)`;
  `CC/list.h:240` `listdeclare(voidP)`. `Blockimplement`/`listimplement` define statics
  (`static T name2(Block(T),_def);`, `GPT errorhandler(list,type) = genericerror;`), so a second
  expansion is a duplicate definition and none at all is an undefined symbol.
- Required include order — these headers name types they do not include:
  `CC/streamdefs.h:39` is `static const int PTRBASE = ios::hex ;` with no include at all;
  `CC/iomanip.h` includes only `<generic.h>` (`:16`) yet uses `ios`, `istream`, `ostream`,
  `iostream` throughout and instantiates `IOMANIPdeclare(int)`/`IOMANIPdeclare(long)` at `:105-106`.
  Both must follow `<iostream.h>`. `CC/stream.h:16-18` is the correct order:
  `#include <iostream.h>` / `#include <iomanip.h>` / `#include <stdiostream.h>`.
- `CC/fstream.h:19` `static const int openprot ;` — declared, not initialised, and then used as a
  default argument at `:27`, `:55`, `:60`, `:76`, `:83`, `:91`, `:98`, `:107`, `:113`. Its
  definition must exist in libC or every `filebuf::open` call is an undefined symbol.
- `CC/iostream.h:565` and `oCC/iostream.h:571` both point at an implementation file by name:
  `static int	stdstatus ; /* see cstreams.c */`.
- `CC/task.h:49-91` expands `task_error_messages` once with `macro_start`/`macro`/`macro_end`
  defined, then `#undef`s all three. A second expansion needs them redefined; the header does not
  provide that.
- `CC/bignum.h:242-243` `overload Exp;` / `overload GCD;` must precede the inline definitions at
  `:244-247` — cfront requires the `overload` declaration before the second same-named function.

**`oCC/` (old cfront 1.x headers)**

- `oCC/oString.h` insists on ordering three separate times, and says so by construction:
  `:4-7` `#define _OVERLOAD_STAT 1` / `#include <sys/types.h>` / `#include <sys/stat.h>` /

- `oCC/complex.h:5-13` the same pattern: nine `overload` lines (`overload cos;` … `overload abs;`)

## contradictions and traps

**1. Four committed headers are absent from the working tree, so this whole scan has a hole.**
`v10/usr/include/CC/u_Regexp.h`, `CC/u_String.h`, `oCC/u_Regexp.h`, `oCC/u_String.h` are all in
`git ls-files`; none exists on disk (`[ -e ]` fails for all four); and `grep` over
`work/v10-fullscan/chunks/` finds them in **no chunk list**. They are the case-collision twins —
the tape's `Regexp.h` and `String.h`, renamed by the `u_` rule.

**2. The `u_` rename broke an include that the source spells by hand.** `CC/u_Regexp.h:5` (from
`git show`) is `#include "String.h"` — a quoted include of a filename the rename removed from the
tree. As shipped in `v10/`, `Regexp.h` cannot resolve its own dependency under either spelling.

**3. Two different headers claim the same include guard, so one silently wins.**
`oCC/oString.h:1-2` is `#ifndef STRING_DOT_H` / `#define STRING_DOT_H`; the absent-but-committed
`oCC/u_String.h` opens with the *identical* two lines and different contents (10374 bytes vs
9913). Whichever is reached first turns the other into a no-op. `CC/u_String.h` uses that guard too.

**4. `STREAMH` is the guard for three mutually exclusive stream packages.** `oCC/stream.h:4-5`
`#ifndef STREAMH` / `#define STREAMH`; `oCC/iostream.h:2-3` the same two lines; `CC/stream.h:13-14`
the same again. In `oCC/`, `<stream.h>` and `<iostream.h>` cannot both take effect — and
`oCC/list.h:5`, `oCC/oString.h:17` and `oCC/complex.h:2` all do `#include <stream.h>` while
`oCC/iostream.h` is the newer package for the same job. Include order decides which class
`ostream` means.

**5. `size_t` has two incompatible definitions inside `CC/`.** `CC/types.h:27` `typedef	long	size_t;`
against `CC/sys/types.h:41` `typedef	unsigned	size_t;`. `CC/stddef.h:8`, `CC/malloc.h:4` and
`CC/new.h:6` each independently say `typedef unsigned size_t;` guarded only by their own
`__STDDEF` / `__MALLOC__H` / `_NEW_H`, so including two of the three is a duplicate typedef.
`CC/types.h` is byte-identical to `oCC/sys/types.h` — so asking `CC/types.h` and `CC/sys/types.h`
the same question gives two answers, and the one that agrees with `oCC` is the *wrong* one for
the `size_t` used by `CC/malloc.h`.

**6. `#include <sys/param.h>` has no target inside either C++ tree.** `CC/types.h:35` and
`oCC/sys/types.h:35` both do it; `git ls-files` shows `CC/sys/` holds only `stat.h times.h types.h`
and `oCC/sys/` only `stat.h types.h`. The file exists solely at `v10/usr/include/sys/param.h`, so
the C++ include path must be `…/CC` *followed by* `/usr/include`. Note the failure is quiet — both
files wrap it in `#ifndef NBBY` with a fallback at `:37-38`, so a wrong include path yields a
compiling but differently-configured header.

**7. `#include <memory.h>` likewise resolves only from inside `CC/`.** `CC/iostream.h:15`
`#include <memory.h>` with the comment `/* Some inlines use memcpy */`, and `CC/string.h:23`
`#include <memory.h>` as the file's last line. `git ls-files` confirms there is **no**
`v10/usr/include/memory.h` — only `v10/usr/include/CC/memory.h`. A build that puts only
`/usr/include` on the path dies at the first `<iostream.h>`. Same for `<generic.h>`
