# 2026-08-22 — task #13: the instrument was broken three ways, and four mechanisms are now excluded

Task #13 is the last substantive open item on Track B: netfs costs **0.84 ms in
the server and 9.46 s in the guest**, and the server, the wire, dropped frames
and retransmission-from-loss were all reported as excluded. The plan for today
was simply to run the instrument CLAUDE.md described as *"built and unused"* —
`V10_IL_TRACE=work/il.trace bash tools/v10-netread.sh`.

**It was built wrong, in three independent ways, and every one of them fails
silently.** None is visible from the simulator's behaviour and none would have
appeared in any assertion. That is the day's main finding, and it is worth more
than the measurement it was blocking.

---

## 1. The trace could not have answered the question it was built for

All three faults are in open-simh, and all three are defaults.

### `set debug -t` on its own is an error

`v10_iltrace` emitted two commands, `set debug <file>` then `set debug -t`.
`sim_set_debon()` (sim_console.c) opens with

	if ((cptr == NULL) || (*cptr == 0))        /* need arg */
	    return SCPE_2FARG;

and the command parser has already consumed `-t` as a switch — so the argument
is empty and the command fails with *"Too few arguments"*. `sim>` printed as
usual, and `v10_boot`'s generic `v10_must "sim>"` accepted it. **A silent
failure in the command whose entire purpose was to add the timestamps.**

### And the timestamp is not a default

sim_console.c:2358 does force `-T` on:

	if (!(sim_deb_switches & (SWMASK ('A') | SWMASK ('T'))))
	    sim_deb_switches |= SWMASK ('T');

but that line sits **inside** `if (sim_deb_switches & SWMASK ('R'))`, so it
applies only when `-R` was asked for. A bare `set debug <file>` timestamps
nothing at all. I had read this block once and taken the default from it.

### Worse: the default filter DELETES retransmissions

scp.c's `_sim_debug_write_flush()` collapses consecutive identical debug lines
into `same as above (N times)` unless `-F` is given. **A retransmitted frame is
by definition an identical hex dump** — so the one hypothesis the trace existed
to test is the one the filter erases, timestamps and all.

There is a third elision inside the dump itself. `eth_packet_trace_ex()` writes
`%04X thru %04X same as above` for a 16-byte group it judges identical to the
one before — on the strength of `eth_mac_cmp`, which compares **six** bytes. A
hex dump from it is therefore not a faithful record of the frame.

### And then the path was wrong

Fixed to one command, `set debug -tf <file>`, the run answered

	sim> set debug -tf work/il.trace
	File open error
	sim> set il debug=PKT;DAT

because `v10_boot` does `cd $V10_MEDIA` before spawning, so the simulator's cwd
is `work/v10gold/` and a relative path lands under a directory that does not
exist. `sim>` followed; the generic prompt-match passed again. **The same shape
of silent failure, twice in one instrument, in one afternoon.**

Fixes, all in `tools/v10drive.exp`:

* one command, `set debug -tf <file>` — switches are case-insensitive and
  combine in one word (`get_switches()` ORs `SWMASK (sim_toupper (c))`), and
  `sim_set_deb_switches()` runs from the same invocation that names the file;
* the path is resolved with `file normalize` **at source time**, before the
  `cd` — normalising inside `v10_iltrace` is too late, it is called after;
* and `v10_boot` now **asserts the trace opened**, at boot rather than at the
  end of the run: `sim_open_logfile()` creates the file the instant it
  succeeds, so its existence is a marker only the success path can write.

*A diagnostic that cannot fail is not a diagnostic; one that deletes its own
evidence is worse, because it produces a file that looks like a reading.*

## 2. `tools/il-gaps.py` — and it guards the trace rather than trusting it

The analyser decodes Ethernet → IP → TCP out of the hex dump and reports the
gap structure, because the question is not *how long* but *between which two
frames*:

	host->guest is il-read    (il_deliver, pdp11_il.c)
	guest->host is il-write   (the transmit path)

so a gap bounded by *host->guest then guest->host* is the guest thinking, and one
bounded by *host->guest then host->guest* is our reply being held up. It also
reports duplicates by `(direction, seq, length)` — the only way to see a
retransmission, since `show il statistics` counts frames and a retransmitted
frame is a perfectly good frame — and the guest's advertised window.

It **refuses** rather than interpolating when any of the three elisions above is
present, and refuses a trace with no timestamps. All three refusals and the
good path were proved against synthetic traces with a planted 9.4 s gap and a
planted retransmission, which it located and classified correctly.

## 3. Four mechanisms excluded, host-side, before any run

### The MSS is a red herring, and it is a good one

V8 sets `tcp_maxseg = 1024`; **V10 sets it to `4096 - sizeof(struct tcpiphdr)`
= 4056**, with the comment *"to fit in a 4k block"* — sized for Datakit's
stream blocks, not for Ethernet's MTU. That looks decisive and is not: SLiRP's
`tcp_mss()` computes

	mss = min(IF_MTU, IF_MRU) - sizeof(struct tcpiphdr);   /* 1500 - 40 */
	if (offer) mss = min(mss, offer);

so the guest's 4056 offer is clamped to **1460 in both directions and nothing
fragments**. Worth recording precisely because it would have been an attractive
wrong answer. `tcpconfig`'s own default is 1024 — the value V8 hardcodes — but
`/etc/rc` runs `tcpconfig /dev/ip6` with two arguments, and the `TCPIOMAXSEG`
ioctl is issued only with a third, so the live value really is 4056.

### The delayed ACK is identical

Both editions run `tcp_fasttimo` at `HZ/5` = 200 ms with the same `TF_DELACK`
handling. Not a difference.

### The window-update path is present, and identical to V8's

`tcpdisrv()` in `tcp_device.c` is structurally the same in both editions, down
to `qenable(OTHERQ(q)); /* update remote send window */`, and `tcpdrinit`'s
high-water is **2048 in both**. So the receive queue does force at least one
window update in the middle of every 4096-byte reply — that is structural — but
it is not something V10 does and V8 does not.

### Frame loss in our own device model: a real bug, and NOT this one

`il_svc()` guards its loop *continuation* on `il.rxq_count` but its **first
`eth_read()` is unconditional**, so when the guest has no buffer posted and a
frame is waiting, the frame is pulled out of `sim_ether`'s 200-entry FIFO and
`il_deliver()` destroys it — `eth_read()` under `USE_READER_THREAD` calls
`ethq_remove()`, so it is gone rather than deferred. The exposure is real and
V10-specific: V8's `ill.c` posts a **full-MTU** buffer from inside `ilrint()`,
so a buffer is always ready when the interrupt returns, while V10's
`ilrcvbufs()` posts 1024-byte blocks one command at a time and **refuses while
a command is active** — and a 1514-byte frame needs two of them.

**It is nevertheless excluded as the cause, by nineteen separate readings.**
`il.ierrors` is incremented on exactly that drop and is what `show il
statistics` prints as *"receive errors"*, and across every logged V10 run —
including ones carrying 2,364 and 2,604 packets — it reads **0**. So the path
never fires. Left as a latent bug with its reasoning recorded, not patched on
suspicion: *a fix aimed at a mechanism that is already measured not to occur is
not a fix.*

## 4. netfsd now reports the distribution, not just the total

The instrument added on 2026-08-20 separates its own service time from time
blocked on the guest, which is what retired the "9.6 s per request" rate error.
But a **total** cannot distinguish a fixed cost from a heavy tail, and those are
different bugs: a fixed cost is a timer or a round trip, a heavy tail is a
backoff. So `Server.swift` now carries the wait *before* each request on that
request's own trace line — which also shows **which** operation the wait
precedes, since a gap before an `NREAD` is not the same finding as a gap before
an `NNAMI` — and prints a histogram at close whose bucket edges are the
candidate mechanisms rather than round numbers:

	V10's minimum retransmit timeout   TCPTV_MIN = 1*PR_SLOWHZ + 1 = 2 s
	V8's                               TCPTV_MIN = 1*PR_SLOWHZ     = 1 s
	V10's ceiling                      TCPTV_MAX = 120 s  (V8: 30 s)
	SLiRP's persist timer              TCPTV_PERSMIN 5 s -> PERSMAX 60 s

`PR_SLOWHZ` is **1** in both editions, so those constants are literally
seconds. A pile at 2 s reads as retransmission, one at 5 and 10 s as a persist
probe, and a flat few milliseconds as neither.

## 5. TASK #13 IS ANSWERED: OUR DEVICE MODEL COALESCED TWO RECEIVE INTERRUPTS INTO ONE

The fixed trace answered it on the first run, and the answer was not in the
guest, the server, the wire or TCP's timers. It was in `pdp11_il.c`.

### What the trace shows

	 2.130  gst->host PA  seq=182   ack=64050  len=52   <- request header
	 2.130  gst->host PA  seq=234   ack=64050  len=14   <- and the name
	 2.136  host->gst A   seq=64050 ack=248    len=0    <- SLiRP acknowledges both
	 2.136  host->gst PA  seq=64050 ack=248    len=48   <- THE REPLY
	 3.644  host->gst PA  seq=64050 ack=248    len=48   <- RETRANSMITTED, +1.508 s
	 3.644  gst->host PA  seq=248   ack=64098  len=52   <- guest replies INSTANTLY

The guest had the reply at 2.136 and did nothing with it for 1.5 s. The instant
the **duplicate** arrived it acknowledged and issued its next request, with no
measurable thinking time. So the reply was in guest memory the whole time and
the guest did not know.

Across the sample: **41 of 125 data-carrying frames retransmitted — 33% — in
both directions**, at 1.2, 1.5, 1.8, 2.0, 2.8, 3.3, 3.8, 4.5, 5.0, 5.5 s. That
is exponential backoff off a two-second floor on a one-second timer, which is
V10's `TCPTV_MIN` and `PR_SLOWHZ` exactly. Essentially every segment appears
`x2`. The guest's advertised window never fell below 2028, so the
window/persist stall is **excluded**.

### The mechanism

Two frames arrive in the same millisecond — a pure ACK and the data — because
SLiRP has both ready. `il_svc()`'s read loop delivers them both in one service
call, and each delivery ends in `il_rxpump()` → `il_setrint()`:

	il.csr |= ILCSR_RDONE;
	if (il.rie) { il.rint = 1; SET_INT (ILR); }

`il.rint` is a **flag**, and `il_rint_ack()` cleared it on the vector read. So
two completions before the guest was dispatched raised **one** interrupt — and
`ni1010a.c`'s `il0int()` handles exactly one packet per interrupt and returns
(`is->rnext = NULL` and out). The second frame sat in guest memory, DMA'd and
correct, with nothing to announce it.

netfs is strict request/response, so nothing else is on the wire. The next
receive interrupt was therefore the **sender's retransmission**, and every
exchange advanced at an RTO.

### Why no counter could see it

**Nothing was ever lost.** `show il statistics` read `receive errors: 0`,
`transmit errors: 0`, `Read Queue: Loss: 0` on the very runs that were paying
this — nineteen such readings across the logs, every one of them true and every
one of them irrelevant. netfsd saw no duplicate requests either, because a TCP
retransmission is deduplicated below the application. *The only instrument that
can see a frame that arrived and was not noticed is a timestamped packet
trace.*

### And why V8 never met it

`ill.c` sets `ILOUTSTANDING` to **1**: V8 posts a single receive buffer, so
`il_svc()`'s loop stops after one frame and a second interrupt is physically
impossible to coalesce. V10's `ni1010a.c` keeps `ILRBYTES` = 3000 bytes in
`ILRSIZE` = 1024-byte blocks — three buffers — so it could, and did. **V8 was
immune by accident, which is why eleven months of V8 networking never showed
it, and why the bug read as a property of V10.**

CLAUDE.md's own rule, for the second time on this file: *a limit you measure
through an emulator is a property of your emulator until proven otherwise.*

### The fix

`il.rpend` counts receive completions the guest has not been told about.
`il_setrint()` increments it; `il_rint_ack()` decrements and, if any remain,
**leaves the request asserted** rather than clearing it — which is what a real
board does. SIMH's VAX dispatch raises IPL, so the re-assertion is not taken
until the handler's `REI` drops it: one interrupt per packet, in order.
`ILC_RESET`, `ILC_FLUSH` and `il_reset()` zero the count, and it is a `REG` so
`save`/`restore` carries it.

## 6. The measurement: 1009.4 s of guest wait became 1.5 s

`tools/v10-netread.sh` over one file, three passes, two readers — **the same 154
netfs requests in both runs**, so the protocol did identical work — with
`V10_IL_TRACE` on and netfsd's new per-request accounting:

	                              before        after
	waiting on the guest         1009.4 s       1.5 s     673x
	serving (netfsd's own)         63.9 ms     26.3 ms
	median wait per request        4.941 s     0.000 s
	p90                           12.268 s     0.006 s
	max                           40.912 s     0.238 s

The distribution is the part worth keeping, because a total could not have
distinguished a fixed cost from a backoff:

	before                        after
	   < 100 ms     1               < 1 ms   125
	   1 - 2 s     30              < 10 ms    22
	   2 - 3 s      9             < 100 ms     1
	   3 - 6 s     76                 < 1 s     6
	   6 - 12 s     6
	  12 - 30 s    28
	     >= 30 s    4

**153 of 154 waits were a second or more; now 148 of 154 are under ten
milliseconds.** The old shape — a pile at 1–2 s, a bigger one at 3–6 s and a
long tail to 40 s — is exponential backoff off a two-second floor, and nothing
else makes that shape.

The wire agrees, from the same runs' traces:

	                          before      after
	frames                     1091        492
	trace span              1025.1 s    3.485 s
	data-carrying frames        602        303
	distinct (seq, len)         335        303
	RETRANSMISSIONS             267          0

**`distinct` equals `data-carrying` after the fix: every segment is now sent
exactly once.** Before, 44% of data frames were duplicates. The card's counters
read `receive errors: 0` and `Read Queue: Loss: 0` in *both* runs — they always
did, and they were always true.

### V8 did not regress; it got faster

The rule in CLAUDE.md is that any change to `pdp11_il.c` must be re-checked
against V8, whose netfs was measured at 290 s → 11 s. Both harnesses, on a
clone, golden verified `8ccbf05614e8` before and after:

* `tools/net-selftest.sh` — **exit 0**, all three assertions
  (`NS-HOSTTCP`, `NS-SERVICES`, `NS-DNS`), clean `/etc/halt`.
* `tools/netfs-latency.sh` — the five-pass workload, three runs:
  **15, 13, 17 s**, against the 32 / 47 / 49 s recorded for the committed
  model and 50 / 60 for the hardened one.

That script is documented here as having ~50% variance and being unable to
detect anything under about 2x, which is why three samples were taken: the new
spread (13–17) does not overlap the old (32–49) and is far tighter. V8 was
mostly protected by `ILOUTSTANDING = 1` but not entirely — a frame spanning two
receive buffers raises `il_setrint()` twice as well.

## 7. And the check that should have caught a stale app could not see it

`tools/app-check.sh` compares the built bundle against `app/ipnx` and
`netfs/Sources`. **It did not watch the emulator cores at all**, so this
change — measured, committed, and worth 673x — could have sat in the repo while
the app went on linking an xcframework built from the previous device model.
The same shape as the golden-disk lesson one layer down: *it is in the repo, it
will arrive in the build.*

Two comparisons now, because the chain is patches → xcframework → app and one
does not imply the other:

* the app binary must be newer than `libsimh/patches` and
  `tools/dmdbridge/patches` (libdmd has no patches directory of its own);
* **and each xcframework must be newer than the patches it is built from** —
  found by proving the first gate bites, because the `touch` that made it fire
  was then cleared by an app rebuild that could not possibly have picked the
  change up.

Both were proved to bite and then satisfied. The first version of the second
check carried a `-newermt '1970-01-01'` that BSD find cannot parse; the
pipeline produced nothing, and the check reported *"empty -- cannot compare"*
and passed. **A predicate added for tidiness turned a gate into a rubber
stamp** — it now reports a failure when it cannot read the framework, rather
than an excuse.

## 8. K16 — "V10 cannot have the 5620" was wrong, and the gap is now closed

Asked whether the V10 golden is functionally a superset of the V8 one. Measured
host-side with both filesystem readers, no simulator:

	              V8      V10 (before)
	root entries  583      186
	/usr entries 4300      601
	total        4883      787      -- 4,454 V8 paths absent

The largest single hole was **`/usr/jerq`, 1,723 paths: the entire DMD 5620
userland**, and I reported it as *unclosable*, citing rung 8's finding that the
5620 cross-compiler is documented on the tape but not shipped.

**That was wrong, and wrong in a specific and instructive way: the search behind
it was run across `work/v10` only, and its conclusion was written down as a fact
about "the tape".** There are two tapes.

- **`v8/jerq/sgs/` is the Software Generation System in source** — `comp` (a
  pcc: `cgram.y`, `pftn.c`, `reader.c`, `trees.c`, `match.c`, `local2.c`,
  `macdefs.h`), `as` (`gencode.c`), `ld`, `nm`, `ar`, `size`, `strip`, `dis`,
  `optim`, plus `3cc.c` and `32reloc.c`. `macdefs.h` names the MAC-32 outright.
- **The V8 golden ships them built**: `3cc` 14,336, `3as` 67,584, `3ld` 77,824,
  `3nm` 24,576, `3ar` 24,576, `3size` 15,360, `3strip` 26,624, `32ld` 17,408.
- **`v8/jerq/src/` is the 5620 userland in source**, 1,677 files; `v8/blit/` is
  the 68000 Blit's, 1,015.

*A negative established by searching one tree is a fact about that tree.*

### What was installed, and why it is not a transplant

The 5620 software arrived on its **own distribution tape** and was installed
into `/usr/jerq` — `blit/Road.map` says so in as many words, and it is why V8's
golden carries it and V10's tarball has no jerq tree at all. Installing it on a
second machine is what a real site did; it is edition-independent terminal
software. V8 does not build it either — 365 files in `carry.txt` plus 1,248 in
`fromgold.txt`, which is exactly the 1,613 `tools/v8extract.py` reads off the
image, a count arrived at by a completely different code path.

K16 adds a **fourth netfs share** carrying that distribution, plus V10's own
1,521 manual pages, and closes the operational holes:

	                       before   after
	V10 root entries          186     188
	V10 /usr entries          601    4278
	V8 paths absent          4454    1928     -- 57% closed
	/usr/jerq absent         1723       0
	/usr/blit absent          402       0
	/usr/man absent           552     154

30/30 assertions, exit 0, and boot 2 of the disk V10 built reaches a login
prompt. `/usr` is 30.1 MB with 76.7 MB free.

Also closed: **`lost+found` on both filesystems** (V8 shipped without one and it
cost a rebuild — an autoboot `fsck` with an orphan to reconnect aborts to single
user), **`/etc/whoami`** (the machine had no name), and **`fsck -p` on
autoboot** — V10's `init` already passes `autoboot` (`cmd/init.c:160` against
:158 for RB_SINGLE), its `fsck` reads `/etc/fstab`, which this disk has correct,
and its exit codes are only 0 or 8, so unlike V8 there is no
reboot-after-repair branch to write. Prepended to the copied `rc` rather than
rewriting it, and the host asserts the mount and network lines survived.

### And it took two runs, for two defects that both ran silently

**Case collisions.** `/usr/jerq` distinguishes three pairs only by case —
`3cc`/`3CC`, `libc.a`/`libC.a`, `src/lib/c`/`src/lib/C`, all C-versus-cfront —
and on case-insensitive APFS the second of each simply overwrote the first. The
extraction reported "1613 files", the same count as a correct one, and `3cc` was
2,322 bytes of shell where 14,336 bytes of compiler belonged. **The count was
right and the bytes were wrong.** The repo already had the convention
(`tools/v8-import.py`: escape the loser, `3CC` -> `3%43%43`) and the machinery
(`netfs/Sources/NetFS/CaseMap.swift` serves the true name to the guest).

**And then the CASEMAP was in the wrong directory.** `CaseMap` reads
`<share root>/CASEMAP`, and the first version wrote it *inside* the extracted
tree — so it was never found, the guest saw the escaped names, and `3%43%43`
duly arrived on the disk while `3CC` did not. The manifest was inside the tree
too, so 153 KB of sha256 shipped as `/usr/jerq/.v8extract`: build detritus
wearing a system path, which this very harness refuses elsewhere. Both now live
beside the tree, where `find .` inside it cannot see them.

The host-side check that caught it is the one that compares `3cc`'s **size**
against 14336, not its existence — a guest-side `test -s` passes on the wrong
file.

## 9. K16 round two, and the metric that was misleading me

Second tranche, all pure copies: V10's **own** kernel source at `/usr/sys`
(`src/lsys`, 763 files — the exact analogue of V8 keeping its kernel source
there), the rest of r70's headers (336 against the 93 installed, copied with
`cpio -pd` and deliberately **without** `-u` so the variants stage 2 measured as
parseable are not overwritten), V8's `/usr/dict` word list and `/usr/net`
vismon data, and the five `/usr/spool` directories. **34/34, exit 0.**

`src/vol2` — V10's own documentation — was **skipped on purpose**: 55 MB to
close an 82-path gap, on a filesystem with 76 MB free. Recorded rather than
done.

**And then the path diff said `/usr/sys` had gone from 202 missing to 199, which
read as a failure of the whole copy.** It is not: V8's kernel-source
subdirectories are `alice boot conf kdi pcs` and V10's are `md io os fs astro
ml`, so installing V10's own tree closes nothing *by path* while taking the tree
from absent to 785 files. A path diff is the right question for a command --
`awk` either exists or it does not -- and the wrong one for a source tree.

*A metric that cannot distinguish "V10 has its own" from "V10 has nothing" will
report the second when the first is true.* `tools/v8v10-diff.py` now reports
both ways, by NAME for commands, libraries and device nodes, and by TREE for
everything whose paths are properly V10's own. Its tree threshold is relative
for the same reason: a fixed one called `/lost+found` at 1 of 1 "thin" and
`/usr/games` at 2 of 154 "ok", both backwards.

### 10.1 The devices: 381 of 382, and only one is impossible

Every group turned out to be a config line rather than a missing driver, once
the majors were read off V10's own `lsys/lib/tab` instead of assumed.

**`/dev/pt/pt00`..`pt63` are NOT pseudo-ttys**, which is why 64 names read for
months as V8 hardware V10 lacks. V8's own `cdevsw` says what they are:

	/*sp*/	nodev,	nodev,	nodev,	nodev,	/*18*/
		nodev,	nulldev,	&spinfo,

`spinfo` is the **stream pipe**. V10 ships the same driver as `lsys/io/spipe.c`
exporting `spcdev`, and mkconf's own catalogue already knows how to configure
it — `lsys/lib/devs` line 64 is `pt sp count data struct queue *spipes`. The
only thing missing was the table entry, and `lsys/lib/tab` carries it
**commented out, with a question**: `# cdev 18 pt   # remove?`. Sixty-four
device names hung on one comment character and a driver nobody had removed.

The rest, each with its evidence:

	group          n    V10's answer
	/dev/fd/0..127 128  cdev 40 is `fd' in BOTH editions; `stdio 0' already
	                    configured.  Every V8 script that opens /dev/fd/3 works.
	/dev/dk/dk01.. 95   cdev 31 is `kdi' in both; ipnx780.m already has `kdi 1'.
	ra00..rra27    45   V8 numbers partitions with a DIGIT where V10 uses a
	                    letter -- aliases for the same minors, not new hardware.
	rp0a..rrp1h    32   bdev 0 / cdev 4 `hp' in V10's own tab, driver
	                    lsys/io/hp.c in V10's own tree, `hp hp mb ...' in
	                    lsys/lib/devs -- and NO config on the tape uses it.
	                    SIMH's vax780 puts RP on MBA0 at nexus 8, which is
	                    alice.m's own number.  This one is a real capability:
	                    it is what lets V10 read an RP07.
	mt/rmt/nmt     12   seki.m's own `mba' + `tm03' + `te16' lines, and SIMH's
	                    MBA1 carries exactly a TM03.  H_NOREWIND is 04 in V8's
	                    mt.c, V10's te16.c and V10's tu78.c alike, so V8's own
	                    minors transfer untranslated.
	kUmem, mtpr     2   V10's mem.c documents the same minors V8 uses.
	kmc0, dn0       2   configured-but-absent, the argument ipnx780.m already
	                    makes for kmc11b: autoconfig probes, finds nothing.
	ip16            1   a PROTOCOL number, not a unit number.

**`kmemr` is the one that cannot exist, and V10 says so itself**: it is mem
minor 4, which V8 calls *"public part of kernel memory (read only)"* and V10's
`mem.c` calls **"obsolete"** with the `case` deleted. A node for it would open
and read nothing. Recorded rather than fabricated.

`proto-dev` went from 80 nodes to 466.

### 10.2 The commands: 94 built, 76 carried, 0 left

Four pieces of machinery, in order of what each was worth.

**(a) The build is now IN-TREE, which was thirty-four "facts about the tape".**
K15 met this building `mux` and the fix was the same; the world survey met it
thirty-four times and I read each as a defect:

	/n/v10/src/cmd/f77/data.c: 2: Can't find include file defs
	/n/v10/src/cmd/neqn/diacrit.c: 3: Can't find include file e.def

`defs` and `e.def` are **in** `cmd/f77` and `cmd/neqn`, and `-I$SD` was on the
command line for both. netfsd's trace settles what happens rather than why: cpp
never looks — the name appears once in the whole trace and that once is `make`
stat'ing a prerequisite — while an angle-bracket include in the same run is
searched for three times. The tape never meets it because every mkfile compiles
in the source directory.

So `worldc.sh` copies the unit to local disk and compiles there. `cp f1 ... fn
d` is V10's own (`cmd/cp/cp.c`: `r |= copy(...)` in a loop), so a directory in
the glob fails that one copy and the rest still land — which is why this needs
neither `find` nor `cpio`. One level of subdirectory is enough, and that is
**measured**: 111 of `world.units`' source paths carry a `/` and the deepest
carries exactly one.

**(b) The commands are not all under `cmd/`.** Surveying only `cmd/` reported
that absence as a property of the tape — the same shape as "the 5620's compiler
is not on the tape", which was a fact about one tree stated about the project.
Four more roots, and nothing in the format changed: `world.units` names a
directory relative to `cmd/` and `worldc.sh` computes `SD=$UD/$dir`, so a unit
rooted at `src/games/atc` emits `../games/atc` and the guest reaches it with no
new field and no new code.

	games     ~20 loose .c plus atc/ mille/ rogue/ sail/ trek/
	lbin      Mail, csh, kermit, mailx -- the Berkeley userland V8 carries
	dregs     xstr
	local     restor variants
	ipc/bin   rcp

358 units became 427. The install paths come from V8's measured `where.txt`,
which is the right oracle here: V10's manual does not document games at all,
and V8 says `/usr/games` for the twenty of them, `/bin` for csh.

**(c) 206 programs in 60 multi-main units.** `world_link`'s own comment
deferred this — *"which objects belong to which program is in each unit's own
makefile, and writing those out is mkdep.py-scale work ... so they are named,
with the count, and left for the phase that generates a makefile per program."*
This is that phase, and it generates nothing: it reads the rules the tape has.
Three witnesses, all the tape's:

	explicit   `cc -o pack pack.o', `cc -o decrypt decrypt.o $(OBJS)'
	implicit   `11cc:  11cc.c' -- a target naming one source and no recipe,
	           letting make's built-in rule link.  The cmd/docgen shape.
	a.out      the tape's DOMINANT idiom, and the first two miss every one:

	               a.out:  awk.g.o awk.lx.o $(OFILES) $(ALLOC) awk.h
	               install:        a.out
	                       cp a.out /usr/bin/awk

	           so the program's NAME comes from the cp destination and its
	           OBJECTS from the a.out target.

That is what closes `awk`, `troff`, `ex`, `dc`, `cb`, `at`, `csh`, `rogue`,
`mille`, `unpack`, `encrypt`/`decrypt`, the asd package tools and seven of the
eight PDP-11 cross-tools. Eleven units still have no recognisable rule
(`cmd/worm`'s 22 programs among them) and are recorded as such rather than
guessed at — pairing each `main` with all the unit's objects would give
`cmd/awk` a `maketab` carrying the whole of awk.

**(d) A command can be a second NAME for a binary**, and reading `nlink > 1` off
the V8 image settles a cluster I had been counting as separate missing commands:

	edit = ex = vi = view      ONE inode, four names
	2 = 3 = 4 = 5 = 6          one file, five names
	more = p = pg              one binary -- and V10 HAS cmd/p
	uncompress = zcat          one binary
	rogue = rogue52            one binary

So V10 building `ex` closes four names rather than one. A hard link is the
filesystem stating the fact. The tape's own `ln /usr/bin/= /usr/bin/==` lines
are read first, because V10 stating its own aliases outranks anything inferred.

Three refusals, each of which produced a wrong row first: an alias equal to its
own target (`ex /usr/bin ex`, from a macro); an alias for a name something
already **builds** (`decrypt`, which `world.prog` links from its own objects);
and a destination outside the command directories, which is how twelve man
pages arrived in a list of commands.

### 10.3 The policy, stated once and applied three times

CLAUDE.md already settles the shape one edition down: a shipped disk carries
*"what V10 built, and the tape's binaries only where we cannot build the
program"*. K17 extends the same rule across the edition boundary, because it is
the same question:

	V10's build          94 of the 170 names
	V10's tape binary    where the tape ships one and we cannot build it
	V8's file            where NEITHER edition has source -- 766 files

`v10/mk/gen/fromv8.txt` is **derived** from the two images, never written by
hand: (what the V8 golden has) minus (what the build produces) minus (what the
V10 golden already has). 615 data, 49 script, 102 binary — and the risk is
confined to the third column. 112 of 128 syscall slots hold the same call at
the same index in both editions, and the reverse direction is already proven at
9/9 by `tools/v10-probe.sh`, so a carried binary is a **candidate rather than a
guarantee**. The data and the scripts cannot fail at runtime at all, and they
are most of it: `/etc/services`, `/etc/termcap`, the fortune database, quiz's
subject files, 78 documents, the spool directories.

Five case collisions had to be escaped on the way (`tab300S`/`tab300s`,
`ideal/lib/{ARC,Arc,arc}`) — the same trap that made `3cc` 2,322 bytes of shell
wearing the compiler's name, and the same fix: `tools/v10-carry8.py` reuses
`v8extract.py`'s own collision machinery and writes CASEMAP at the **share
root**, which is the only place `netfs/Sources/NetFS/CaseMap.swift` reads it.

### 10.5 Two faults found by running it, both in the flattering direction

**`ld` WROTE A KERNEL THAT CANNOT BOOT AND THE RUN EXITED 0.** The first kernel
build with the new config reported 21/22 and *"ipnx780.u is 310300 bytes -> 
plausible: a linked 780 kernel"* — 80 KB larger than the 230,371 before, which
is `hp.o`, `te16.o`, `tm03.o`, `dn.o` and `tu78.o` being pulled in and is
exactly right. Buried at line 220:

	Undefined:
	_spcdev

**A driver's source being on the tape is not its object being in the tape's
archive**, and K6/K7 link archives. `ar t` over all eight of `lsys/lib/*.a`
finds `hp.y`, `te16.y`, `tu78.y`, `dn.y`, `kdi.y`, `fd.x` and `mba.y` — and no
`spipe`. So `cdev 18 pt` could not work however good `lsys/io/spipe.c` is.
V10's `ld` writes its output with symbols undefined (it reports them and clears
the execute bits), so this is the **third** time that behaviour has produced a
confident wrong answer here: stage 3's `Undefined: _atof`, a diagnostic that
"re-ran" a failed link and printed success, and now a kernel.

The fix is `KERNEL_ADD` in `v10/mk/mkdep.py`, and `kobj.order` gained a fourth
column: `ours` for a patched copy under `v10/src`, `tape` for a driver no
archive contains. It **cannot** be an overlay entry — every file in `v10/src` is
*"derived from a named upstream file with a stated sha256 and one stated
substitution"*, and there is no substitution to state. A verbatim copy there
would be a lie about what the tree is. And `mkdep.py` raises rather than
skipping if a `KERNEL_ADD` object turns out to be in an archive, because a guard
that quietly declines to fire is indistinguishable from one with nothing to do.

**AND THE CARRY LIST WAS EXCLUDING NAMES ON THE STRENGTH OF AN INTENTION.**
`fromv8.txt` skipped anything with a `world.*` row — but a row says the build
*intends* to install a name, not that it succeeded. K10.3 linked 203 of 251, so
48 names had a row and no binary, and excluding those loses them from **both**
sides: not built and not carried. `compress` is the case that would have bitten,
taking `uncompress` and `zcat` with it, since both are aliases pointing at a
binary that never linked. `V10_BUILDER=<image> tools/v10-fromv8.py` now measures
the staged root instead — the artefact outranks the intention, which is the same
argument that reads `libc.a`'s member order out of the archive.

Measured against the OLD staged root (203 names) the carry list is 912 files
rather than 766; the difference is 146 names the rows claimed and the build did
not deliver.

**AND CONFIGURING THREE DEVICES PULLED IN A FOURTH.** The second kernel build
resolved `_spcdev` and failed on

	Undefined:
	_drcnt
	_drreg
	_draddr

which names no device. It is the **DR-11C**, and `lsys/io/drbit.c` explains
itself in its own header: *"The routines in this driver are not called through
the normal device interface. Instead, they are available for other device
drivers to use to send arbitrary information out on a DR-11C."* So `hp`, `te16`
or `dn` calls `drsetbit()`, `drbit.y` joins the link, and mkconf emits
`drcnt`/`draddr[]`/`drreg[]` only for a configured device — the `kmc11b` case
one device along, and `research.m` has the line verbatim.

`tm03` looked like the next one: it is in no archive and `te16.c` calls
`tm03init()`. It is not. Parsing `io.a`'s own `__.SYMDEF` shows `_tm03init`
**defined in `te16.y` itself**. *A missing member name is a question about
symbols, and the archive answers it directly* — one twenty-line dump instead of
a twenty-two-minute rebuild.

**AND A THIRD, WHICH IS THE OLDEST LESSON HERE WEARING A NEW FACE.**
`tools/v10-netboot.exp` carried

	set DISKTOOLS {find chmod ls cpio grep wc}

beside `mkdep.py`'s `BOOTPATH`, and asserted *"every disk tool has a row in
bootpath.order"* as `llength $toolrows == llength $DISKTOOLS` — **a list
compared with itself**. Adding `ln` to `BOOTPATH` left the harness building six
tools and reporting **33/33**; only a host-side `stat` of the finished image
found `/bin/ln` absent. `mkdep.py` emits `disktools.ord` now and the harness
reads it.

Two lessons, and the second is the sharper one: *a component list that appears
twice will disagree*, which this project already knew — and *an assertion whose
two sides come from the same statement is not an assertion*, which it did not.

### 10.7 The in-tree diagnosis was wrong, and the run said so

Thirty-four units failed like this and I read each as a compiler defect:

	/n/v10/src/cmd/f77/data.c: 2: Can't find include file defs
	/n/v10/src/cmd/neqn/diacrit.c: 3: Can't find include file e.def

`defs` and `e.def` are in `cmd/f77` and `cmd/neqn`, `-I$SD` was on the command
line for both, and K15 had met something that looked identical building `mux`.
So the fix was to build in-tree, as K15 did. **The message after the change
was `./data.c: 2: Can't find include file defs`** — the source local, the
header still not found.

The real cause is four lines away from where I was looking. `sources()` collects
`.c`, `.h`, `.s` and the generator suffixes; `world_cpio()` copies exactly that
set to the courier disk; and the tape also writes headers called **`defs`,
`defines`, `e.def`, `manifest` and `trace.d`**. Those files were never on the
disk. A missing file, reported as a compiler defect, for thirty-four units.

Checked host-side in one command once the idea arrived:

	f77/defs        world.cpio:0   on-disk:NO
	neqn/e.def      world.cpio:0   on-disk:NO
	cflow/manifest  world.cpio:0   on-disk:NO
	trace/trace.d   world.cpio:0   on-disk:NO
	dc/dc.h         world.cpio:1   on-disk:yes    <- the control
	descrypt/crypt.h world.cpio:1  on-disk:yes    <- and another

`dc` and `descrypt` both build, both with a quoted local include, which is what
kills the cpp theory outright.

**Two things made this cheap, and both were deliberate.** The counter-evidence
was already in this project's own kernel build — K7 compiles `streamio.c`
out-of-tree with a quoted `"sys/param.h"` and it resolves on every run — so the
rule could never have been "quoted includes ignore `-I`", and I wrote that
objection into the comment at the time. And the same comment said, in as many
words, *"if these thirty-four still fail after this change, the diagnosis is
wrong and the comment above must be corrected rather than the fix defended."*
They still failed. Writing the refutation condition down before running the
experiment is the only reason this cost one run instead of a week of defending
a fix.

`scan()` records unit-local includes by name now, whatever they are called, and
`world.cpio` carries them — forty more files. `cflow/manifest` stays unresolved
and that is correct: it is `cmd/pcc1/mip/manifest`, another unit's file, and
`resolve()` refuses foreign hits for the reason it already documents (resolving
`ccom`'s `"stdio.h"` to a **Sun** header once made 54 units read as ready).

The in-tree build stays, on its own merits: it is what the tape's mkfiles do,
it is what K15 measured as necessary there, and it removes a whole class of
question about where a header is looked for.

### 10.9 Two `pgrep` traps in one afternoon, and the second is the dangerous one

The chained *"wait for this run, then start the next"* idiom was

	until ! pgrep -f 'tools/v10-srcdisk.sh' >/dev/null; do sleep 30; done

and `pgrep -f` matches the **waiter's own command line**, which contains that
string. So the loop waits for itself; two of them wait for each other. The
srcdisk had finished 53/53 twenty minutes earlier and the netboot never started
— indistinguishable from a slow build. Nothing was damaged: the loops are inert
sleeps and no guest was running.

The obvious repair — *wait on the simulator instead* — has the same defect and a
worse failure mode:

	$ pgrep -f 'vax780' | wc -l
	2
	$ ps -o pid,ppid,command -p ...
	2959  /bin/zsh -c ... until ! pgrep -f 'vax780' ...
	3183  .../work/opensimh/BIN/vax780

**One simulator, and the count says two** — which in this project is the single
most alarming false positive there is, because two simulators on one disk is the
central corruption hazard. Two forms are safe: break the literal
(`pgrep -f '[v]10-srcdisk.sh'`) or match the process NAME
(**`pgrep -x vax780`**), which is what `tools/app-check.sh` already does for
`pgrep -x ipnx`. And when a count looks wrong, print `ps` before believing it.

### 10.12 The fit check refused a disk that fits, and it was right to be strict

K18 answered

	root  needs   1396 of   1280 blocks (109% full, -116 spare)   <-- DOES NOT FIT

and refused, which is the behaviour that matters: **a full V10 filesystem does
not fail, it sleeps**, so a fit check that guesses high costs a run and one that
guesses low costs an unattended hang. This one guessed high, and the reason is
the rule this project keeps relearning — *the host's model has to be what the
guest does*.

`base` walked all of the builder's `/`. The copy takes
`foreach d {bin etc lib dev}` plus `/unix`. The builder's root also holds:

	/tmp   39 files, 554 KB  -- K13's build scratch, including SECOND copies
	                            of fsck, login, nafsmnt and dipconfig
	/n     mount points

Neither is copied, and counting them was 178 blocks of phantom. Corrected, the
same disk needs **1,217 of 1,280 — 63 blocks spare**, and the harness says
`under 5% spare` rather than refusing.

Two things worth keeping. The error ran in the **safe** direction, which is the
only reason it cost a run rather than a corrupted image — and that is not luck,
it is what "refuse rather than proceed" buys. And the 5 MB root really is nearly
full: Bell Labs sized partition `a` to 10,240 sectors and this disk now carries
303 units' worth of built commands plus 45 carried files in `/bin`, `/etc` and
`/lib`. There is no headroom left for a fourth thing without moving the
geometry, which `alice.m` and `seki.m` both argue against.

### 10.13 The disk booted, reached `login:`, and was unusable

K18's second boot came up perfectly — kernel banner, autoboot `fsck`, the motd,
the network line, `ipnx-v10 login:` — and then:

	login: root
	Password:

Root had a password. The whole symptom was one prompt.

`v8/mk/where.txt` carries **two** rows for `passwd`: `/bin` for the command and
`/etc` for the password **file**, which `harvest-paths.sh` recorded because it
is a regular file in a directory the harvest walks. `v8_where()` takes one of
them and it took `/etc`, so `world.script` emitted

	passwd /etc . passwd.sh

and the disk shipped V10's `cmd/passwd.sh` **as `/etc/passwd`**. Reading it off
the image with `tools/v10fs.py` is unambiguous:

	#!/bin/sh -p
	PATH=/bin:/usr/bin
	...
		/bin/passwdx $*

Two guards, because a generator guard and a disk are different things.
`world_script()` and `world_alias()` now refuse any destination whose basename
is in `proto-etc`'s own first column — `passwd group ttys rc motd fstab mtab
utmp profile`, *"the tables and the empty files a machine needs to come up"* —
and say so on stderr rather than dropping the row silently. And
`v10-mkdisk.exp` asserts the **artefact**: `sed -n '/^root:/p' $MP/etc/passwd`.

The general shape is one this project already knows in another guise: a name
that means two things in two namespaces. `world.link` was safe only by luck —
V10's own `where.txt` has no `passwd` row at all, so the command never competed
for the path.

### 12.1 Why root is full, since it is now a standing constraint

	partition a = 10,240 SECTORS = 1,280 blocks x 4096 = 5.0 MB
	              (ra_sizes[] in lsys/io/ra.c -- Bell Labs' geometry)

	/bin     61 files  1974 KB   534 blocks
	/etc     73 files  1359 KB   396
	/lib      9 files   747 KB   198
	/unix     1 file    237 KB    61
	content 144 files  4318 KB  1189
	i-list                         19
	dirs + boot                   ~12
	FREE                           60      245 KB, 95% full

Three causes and none is avoidable without moving the geometry: the partition is
1985's and the V10 golden's own root was sized to it exactly; K17 put a 303-unit
userland's root half in it (89 programs destined for `/bin` and `/etc`) plus 45

tape, stream-pipe and DR-11C drivers; and **10% is lost to internal
fragmentation** -- 4,318 KB of data occupies 1,189 blocks of 4,096 = 4,756 KB,
because most commands are far smaller than a block.

Growing it means editing `ra_sizes[]` **and** moving swap, which starts at
sector 10,240 immediately behind root. That is a kernel change and a geometry
deviation, and K14 already argued against exactly that: `alice.m` and `seki.m`
both say `root regfs ra 0100`, so a whole-drive or resized root is ours and not
theirs.

### 12.2 A fourth case collision, and this one was LOUD

Admitting `/usr/bin/WWB` produced

	IsADirectoryError: .../work/v8dist/root/usr/bin/wwb

because V8 has **`/usr/bin/WWB` (a directory) and `/usr/bin/wwb` (a regular
file)**, and on case-insensitive APFS they are one name. `resolve_collisions()`
did not catch it: it registers the **leaf** of every path, and a directory
exists only implicitly, as a prefix of the files under it. `usr/bin/WWB` was
never compared with anything.

`stored()` already walks components and renames each in turn — the machinery was
built for exactly this and simply was not being told about the directories.
Registering every prefix fixes it, and the map now reads

	root/usr/bin	%57%57%42	WWB

so netfsd serves the true name and no copy step has to know.

**This is the loud version of the failure the whole mechanism exists for.**
`3CC` silently overwriting `3cc` left a 2,322-byte shell script wearing the
compiler's name and an identical file COUNT; this one raised an exception on the
second write. The silent one is why the size of `3cc` is asserted rather than
its existence — and re-extracting all four trees through the fixed resolver
keeps that assertion at 14,336 bytes.
